# Migration 10 manual deployment

Use the SkillSwap production Dashboard SQL Editor only after explicit deployment approval and a fresh preflight. Verify the project name and reference against the app configuration. Keep the migration, preflight and postflight in separate editor tabs.

1. Run both statements in `10_preflight_read_only.sql`. Export both result sets as files under a new owner-only directory in `~/Documents/SkillSwap-Private-Backups/`. Include the tested migration hash and capture time. The results contain schema metadata and aggregate counts. Keep them outside Git, make the files owner-only, and record and verify SHA-256 checksums.
2. Confirm the reconnection table and three new RPCs are absent, the pair index is valid, and invalid messages are zero. Compare the existing function bodies, owners, ACLs, table policies and constraints with the reviewed baseline from 05 and 07. Check whether the optional preference table exists and whether it matches 06. Save the original `chat_unblock` and `chat_respond` definitions and ACLs from the export. Investigate discrepancies before approval.
3. After approval, open `10_chat_reconnection.sql` and verify SHA-256 `3963d32f02d2091f49a1e3432fbf878e9ba6d5000b1fc099675510be86048c0f`. Paste the entire file into a fresh query tab, from BEGIN through COMMIT. Run it once during a quiet period. If SQL Editor reports an error, a timeout, or an ambiguous result, stop and inspect the catalog before considering any retry.
4. Run `10_verify_read_only.sql`. Expect RLS with no authenticated direct access on the ledger, validated unique and foreign-key constraints, SECURITY DEFINER RPCs with an empty search path, authenticated execution, and no anonymous execution. Compare replaced function owners and grants against preflight. Check the valid pair index, zero invalid reconnections, and aggregate counts matching the preflight where there was no concurrent student activity. The migration itself creates an empty ledger.
5. Re-run the catalog export to compare deployed RPC bodies with the tested file and verify that 05 and 07 objects outside the intended replacements retain their definitions and grants. Use an authenticated app session for a read-only inbox smoke test. Keep block, unblock, and reconnection writes in a test environment.

## Test environment

Prefer a separately verified hosted staging project. Use a simulator build configured exclusively for staging and two synthetic accounts. Verify exact decoded RPC response fields, original and reversed request direction, block/unblock, read-only history, pending composer restrictions, accept and decline, and the old client response fallback. Exercise accept and decline on separate disposable pairs, which can reuse the same two fixture identities after a staging reset, or use additional synthetic identities. Check that a nonparticipant or anonymous caller cannot see another thread or respond.

If hosted staging is unavailable, initialize and start an unlinked full Supabase stack in a temporary directory. Use a schema-only baseline or fixtures compatible with 05 and 07, apply 10 locally, and point a simulator-only build at the local API with its public client key. Sign in through local Auth as synthetic users and exercise the same flows through PostgREST and SwiftUI. This validates JSON decoding and authenticated behavior on the local stack. Production gateway configuration, deployed PostgREST version and cache behavior, JWT mapping and hosted client compatibility still require a hosted check.

## Recovery

A SQL error before COMMIT rolls back the migration transaction. After COMMIT, revoke or disable reconnection initiation before recovery. Preserve the ledger, particularly each consumed message ID, and preserve the messages themselves. Under a separately approved rollback, close any pending reconnections to a read-only state before restoring the old response function. Restoring the old response function while such a request is pending could give approval authority to the original recipient regardless of the latest request direction. Restoring the old functions alone does not reverse accepted reconnections or reconstruct prior statuses. Capture current counts and definitions before any recovery operation.
