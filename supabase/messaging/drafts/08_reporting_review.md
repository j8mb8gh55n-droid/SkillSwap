# Reporting and moderation review

The original draft derives the reporter from Auth, derives the reported student from conversation membership and accepts evidence authored by that student in the same thread. The revised draft retains those checks and the private RLS setup. It adds five reasons, optional details up to 500 characters, one report per reporter and evidence message per conversation, one general report per reporter per conversation, and five successful reports per rolling 24 hours. A per-reporter lock serializes concurrent submissions. The evidence picker shows messages already loaded in the thread from the other participant.

## Proposed moderator access

No app-level moderator authorization was found in the repository. Confirm hosted configuration before choosing a mechanism. Use a private moderator membership table keyed by Auth user ID if no existing role can be reused. Only a trusted operator can add or revoke membership. Student roles have no direct access to this table or the report table. Check current membership from `auth.uid()` on each moderation RPC so revoked access takes effect on the next call.

Use separate authenticated RPCs for paginated queue summaries, case details, and review or resolution. Only return the selected evidence message within its case. Keep the moderator's identity and timestamp in an append-only action log. Lock the case row while changing status and adding its audit event in the same transaction. Define allowed transitions from pending to reviewed or resolved, and from reviewed to resolved. Use an empty search path and explicit execution grants. Keep purpose, evidence and decision out of routine logs.

Approve moderator provisioning and revocation, review handling, evidence retention and any account-deletion implications before implementing moderator access. Report foreign keys add retention dependencies. Test authorized, ordinary, unauthenticated and revoked identities separately once the mechanism is approved. Include queue access, evidence scoping, transition validity and audit attribution.

## Preflight and rollback

Run the read-only checks before and after installation. Before installation, confirm the report table and all report RPC overloads are absent, PostgreSQL is 15 or later, and 05, 07 and 10 objects match the deployment baseline. Capture function definitions, permissions and aggregate counts in the private backup. After installation, confirm exactly one report signature, authenticated execution, anonymous denial, RLS enabled with zero policies and zero direct student access, and validated foreign keys and uniqueness. Compare messaging counts and existing RPC definitions to the preflight. Use test accounts in a separate environment to exercise PostgREST submission and verification.

The migration is transactional. After deployment, disable entry by switching off `CHAT_REPORTING_ENABLED` in the app and revoke authenticated execution of `chat_report(uuid,text,bigint,text)` if a server-side pause is needed. Preserve the report table and referenced evidence after real submissions. Any later removal requires an approved export and retention decision. The app flag is a presentation gate. RPC grants enforce server access.

Release the native report sheet after approval of the moderator workflow and deployment of the submission RPC. The moderator interface requires a queue, case evidence view and review or resolution controls.

## Moderation draft for review

Apply `08_chat_reports.sql` before `08b_chat_moderation.sql` in a test environment. The student report RPC and submission rules are identical to the tested draft. Moderation adds a private membership table, report status, an action table and three RPCs. Active moderators can review all cases except reports they submitted and reports about themselves. This is the proposed case authorization rule. Approve it before release.

Only the database owner or a trusted operator acting through a privileged database session provisions membership. Confirm the selected account's exact Auth UUID through the Dashboard and verify the account is the intended moderator. After separate approval, the operator inserts that UUID into `chat_moderation_private.members(user_id)` using the SQL Editor. The operator revokes access by setting `revoked_at`. Review the member identity before restoring access. There is no provisioning RPC. The API roles receive no schema or table grants. Membership row locks serialize revocation with calls that have already started. The next call after a committed revocation is denied.

The queue uses a grouped list with Pending, Reviewed and Resolved filters. Show reason, reported profile name, submission date and an evidence indicator. Page using the last row's timestamp and ID. The details screen shows reporter and reported profile names, description, the single selected evidence message, and action history. Offer Mark Reviewed and Resolve only for allowed transitions. Confirm resolution, show errors inline, and reload after server acknowledgment. Treat an access-denied response as a reason to clear cached case data and return to a neutral screen. A successful authorized queue call can gate the moderator route. Keep the student report sheet presentation unchanged. App-level moderator screens are proposed here.

Run the dedicated moderation preflight in the SQL Editor and confirm any role-related metadata or objects with the project owner. The query is a discovery aid and cannot establish absence of an external admin system. Also run the existing report checks and compare 05, 07 and 10 against their captures. Verify production default privileges, function owners and the private schema's API exposure before rollout. Run both postflight scripts and compare the submission definition and existing messaging counts. Expect zero active moderators before bootstrap and zero action rows before moderation starts. Validate the role gates with synthetic sessions in staging, including an authenticated reporter, reported student, unrelated student, and granted then revoked moderator.

A failed transaction rolls back its draft. After commit, pause reporting by revoking student submission execution and removing the student entry point if necessary. Pause moderator access by revoking execution on the three public moderator RPCs. Preserve membership, statuses, audit events, reports and message evidence. Export all five categories privately before considering schema rollback. Restoring a prior app version alone leaves RPCs callable. No automatic retention period is introduced. Existing account-deletion flows are untouched. Report and audit foreign keys can restrict deletion of referenced data, so review deletion policy separately before release. Membership and audit actor UUIDs deliberately avoid Auth foreign keys so moderator account removal does not erase attribution. Privileged database owners remain trusted for administration and can alter the action table. This audit trail is immutable to app clients.
