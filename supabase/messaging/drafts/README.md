# Messaging follow-up drafts

Apply each only after review and after Migration 05. Review existing Storage policies for broad grants before adding the attachment bucket. The deployed project currently has a public avatar bucket and no private bucket.

- **06** keeps mute and inbox hiding private to the signed-in participant. The client must use the filtered inbox view before pagination. Opening a hidden thread from a profile shows its history and keeps it hidden until either student sends another message. Unread cursors remain separate from the hide cursor.
- **07** records who blocks whom. Existing pair-level blocks stay in a protected legacy table because their owner cannot be inferred. Profile → Settings → Privacy & Safety → Blocked Students should join the caller's block rows to profile names and avatars, confirm Unblock, and refresh after success. Removing one's block leaves any other or legacy block in force. When the last known block is removed, the thread becomes read-only and cannot start a new introduction. Product review should confirm wording for this state before wiring the UI.
- **08** allows a signed-in participant to report the other participant with optional reason and an optional selected message from that student. After confirmation, display success only on RPC acknowledgment. Reports are private and require an authorized moderation queue, review and retention policy, and rate limiting before app release.
- **09** requires trusted upload and download endpoints. Derive the sender from a verified token. Validate decoded image type and dimensions, strip metadata, and cap uploads at 5 MiB. The native camera and photo picker should offer a preview before an explicit send. Upload under a server-generated object path, finalize atomically in PostgreSQL, and clean up an unlinked object if finalization fails. Make retries idempotent and handle ambiguous failures by checking whether finalization committed before removing an object. For download, check the requesting participant against the linked message on every request and stream privately. The draft grants no direct Storage access to either client role. Test with the hosted Storage API or a full local Supabase stack before deployment.

Run the read-only verification after each draft. Confirm anonymous RPCs are denied, the finalization RPC is service-only, and Storage policies cannot expose the attachment bucket. Use a separate backup and reviewed rollback before deployment. Preserve reports, blocks and attachment metadata if reversing schema changes after use.
